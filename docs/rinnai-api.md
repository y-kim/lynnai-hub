# 린나이 클라우드 API (rkiot) 규약

린나이 각방 보일러·조절기가 린나이 클라우드(`rkiot.net`)와 주고받는 프로토콜을 정리한 문서다.
LYNNAI 허브(ESP32 펌웨어 `firmware/esp32/`)와 NAS 판(`server/lynnai-nas/`)이 이 규약대로 기기를 받고,
SmartThings Edge 드라이버·Home Assistant 통합이 그 위에서 동작한다.

출처는 린나이 스마트링크 앱(`kr.co.rinnai.app.total`)과 실측이다. 값(사실)만 옮겼다.

---

## 1. 단위

상태 응답(블롭)을 읽는 단위가 기기마다 다르다. 인덱스는 모두 0부터 센다.

| 단위 | 크기 | 예 |
|---|---|---|
| 비트 bit | 1비트 | 0 / 1 |
| 니블 nibble | 4비트 = 16진 한 자리 | `3`, `c` |
| 바이트 byte | 8비트 = 16진 두 자리 | `3c` |
| 블롭 blob | 상태 응답(EPC 70) `data` 문자열 전체 | 보일러 64니블 · 각방 110니블 |
| 슬롯 slot | 각방의 7바이트 묶음 = 한 구역 | slot `s` = `byte[7s..7s+6]` |

- 보일러(f06)는 **니블** 단위(플래그 1니블, 온도 2니블).
- 각방(f09)은 **바이트** 단위(7바이트 슬롯). `byte N = 니블 2N·2N+1`.
- 앱 소스는 1부터 세므로, 앱 필드 인덱스는 이 문서보다 +1 이다.

## 2. 기기 계열

`rkiot` 플랫폼은 전 기기를 같은 J07 메시지 틀로 다룬다. `groupCd` 가 계열(f-코드)이다.

| f-코드 | 계열 | 모델 수 |
|---|---|---|
| `f06` | 보일러 | 37종 |
| `f09` | 각방 조절기 (서머스탯) | 9종 |
| `f0a` | 스팀오븐 | 1종 |

- 모델명 `RINNAI_<계열>_<서브>` = `groupCd`/`groupTypeCd`.
- 쿡탑·인덕션은 이 플랫폼 카탈로그에 없다.

보일러와 각방의 차이:

| 항목 | 보일러 f06 | 각방 f09 |
|---|---|---|
| 상태 읽기 | `fa` → `70` 블롭만 (개별 EPC 읽기 불가) | 〃 |
| 공유 명령 | `b1`·`b3`·`d1`·`72`·`fa` | 〃 |
| 전용 명령 | `80`·`d2`·`b2`·`a5`·`b6`·`b7` | `a0`·`d4`·`da`·`96`/`97` |
| 읽는 단위 | 니블 | 바이트 (7바이트 슬롯) |
| 구역 | 없음 (본체 하나) | 최대 7존, `a0` 로 선택 |

## 3. 접속·토픽

### 3.1 부트스트랩

```
GET http://www.rkiot.net/key/server
← { ip, mqtt: 8883, ssl: true, uid, pass }
```

기기는 이 응답으로 MQTT 서버 주소·포트와 접속 계정을 받은 뒤 MQTT(TLS, 포트 8883)로 붙는다.
`clientId = d:rinnai:RK:01:RK:{MAC}`.

### 3.2 토픽

```
rinnai/RK/01/RK/<f코드>/<서브>/{MAC}/<suffix>
예) rinnai/RK/01/RK/f06/23/{MAC}/set
```

`<서브>` 두 자리가 **모델코드**다(§8).

| suffix | 방향 | 뜻 |
|---|---|---|
| `/get` | 서버 → 기기 | 상태 요청 (`fa`) |
| `/set` | 서버 → 기기 | 명령 |
| `/inf` `/res` | 기기 → 서버 | 상태 보고 (EPC 70) |
| `/stg` | 기기 → 서버 | 사용량 통계·시간 요청 (§7) |

## 4. 명령 (EPC, `/set`)

J07 메시지의 `rpc[].id` 가 EPC, `data` 가 값(평문 16진)이다. ★ = f09 전용.

| EPC | 앱 상수 | 기능 | 데이터 | 상태 |
|---|---|---|---|---|
| `fa` | REQUEST_STATUS | 상태 요청 → `70` 응답 | — | 확인 |
| `80` | POWER | 전원 | 0/1 | 확인 |
| `b1` | HEAT | 난방 (공용) | 0/1 | 확인 |
| `b3` | OUT | 외출 (공용) | 0/1 | 확인 |
| `b4` | HEAT_MODE | f06 온돌(0)/실내(1) · f09 실온(0)/시간(1) ★ | 0/1 | 확인 |
| `b5` | QUIET_MODE | 정음 | 0/1 | 확인 |
| `b2` | CONTROL_MODE | 운전 모드 (enum, §5) | 값 | 확인 |
| `b6` | PREHEAT | 온수 예열 | 0/1 | 확인 |
| `d7` | HOT_WATER | 온수 | 0/1 | 확인 |
| `d1` | HOT_WATER_TEMP | 온수 온도 (공용) | °C 16진 | 확인 |
| `df` | HOT_WATER_TEMP_POINT | 온수 온도 소수 자리 | 0/5 | 확인 |
| `d2` | ONDOL_MODE | 온돌(난방수) 온도 — f06 | °C 16진 | 확인 |
| `d4` | NORMAL_MODE | 방 설정온도 ★ (5~40°C) | °C 16진 | 확인 |
| `a0` | — | 대상 구역 선택자 ★ | slot+1 | 확인 |
| `da` | HEAT_TIME | 시간모드 "1시간에 N분" ★ | 분 16진 (`1e`=30분) | 확인 |
| `96`/`97` | RES / RES_TIME | 예약 on / 시간(1~24h) ★ | 0/1·16진 | 확인(f09) |
| `72` | — | 시간 동기 | `YYYYMMDDThhmmss` | 확인 |
| `a5` | LOCK_MODE | 차일드락 | 0/1 | 미시험 |
| `b7` | RAPID_HEATING | 빠른 난방 | 0/1 | 미시험 |
| `90`/`94`/`95` | RES_24_* | 24시간 예약 | — | 미시험 |
| `9a`–`9d` | PATTERN_* | 패턴 예약 | — | 미시험 |
| `ab`/`ac`/`ad` | AI_MODE·*_AI | AI 모드 (신형 전용) | — | 못 씀 |
| `bd` | SMART_DIAGNOSIS | 스마트 진단 (신형 전용) | — | 못 씀 |
| `ba` | OTA_UPDATE_PERMIT | 펌웨어 업데이트 허용 | — | 안 건드림 |

온도는 소수까지 보낼 때 `d1=<정수 16진>, df=<소수 자리>` 로 나눈다(37.5°C → `d1=25, df=5`).
각방 명령은 `a0`(구역) + 동작(`b1`/`d4`/`96`…)을 한 J07 에 함께 보낸다.

### 4.1 명령이 먹었는지 확인

- 명령은 QoS 0 으로 **한 번만** 가서 가끔 사라진다. 린나이 앱은 2.5초·3번 다시 보낸다.
- 보일러는 4~12초마다 **무관한** 상태 보고를 올리므로 "보고가 오면 성공"은 틀린 판단이다.
  명령이 바꾸려던 칸(f06 니블·f09 슬롯 바이트)을 그 뒤 보고에서 **값으로 비교**해야 한다.
- **메아리 뒤 되돌림**: Wi-Fi 모듈이 받은 값을 바로 상태에 실었다가, 보일러가 안 받으면
  19~23초 뒤 되돌린다. "칸이 바뀜" = 모듈이 받았다는 뜻일 뿐, 보일러가 받았는지는 20초 넘게 지켜봐야 안다.
- 앱이 노출하는 기능 중 일부만 실제 구현된다(f06 반복·24시간·패턴 예약은 수십 초 뒤 원복 = 사실상 미지원).
  → 스케줄은 자동화(HA/ST) 쪽에서 쏘는 것이 맞다.

LYNNAI 허브의 반영은 `firmware/esp32/main/hub_rinnai.c`(값 비교·2.5초·3번·3회 포기).

## 5. 보일러 상태 블롭 (f06, 니블)

`fa` 응답 `70` = **64니블**, 0부터. 플래그 1니블, 온도 2니블(평문 16진).

| 니블 | 필드 | 뜻 |
|---|---|---|
| 0 | opStatus | 전원 |
| 2 | heatStatus | 난방 켜짐 |
| 3 | hotWaterStatus | 온수 켜짐 |
| 5 | preheatStatus | 온수 예열 |
| 6 | lockMode | 차일드락 |
| 7 | heatMode | 난방 모드 (0 온돌 / 1 실내) |
| 8 | heatCombustion | 난방 연소 — 가스 펄스와 맞물림(§7) |
| 9 | hwCombustion | 온수 연소 |
| 10–11 | hwSettingTemp | 온수 설정 (16진) |
| 12 | hwSettingTempPoint | 온수 소수 자리 |
| 13–14 | heatSettingTempOndol | 온돌(난방수) 설정 (16진) |
| 15–16 | heatSettingTemp | 실내 설정 |
| 17–18 | currentTemp | 현재 실내온도 (16진) |
| 19 | outingStatus | 외출 |
| 20 | errorStatus | 에러 플래그 |
| 21–23 | errorData | 에러 코드 (무에러 = `fff`) |
| 24 | echoDetection | 난방 에코 감지 |
| 25 | flowDetection | 물 흐름 감지 |
| 26 | modeStatus | 운전 모드 enum (아래) |
| 27 | frozenAlarmNoti | 동파 알림 |
| 28 | frozenBuzzerAlarm | 동파 경보음 |
| 29–30 | heatTempLimit | 난방 최대 온도 (`55`=85°C) |
| 31–38 | sw_01..08 | 조절기 조작 기록 (방 정보 아님) |
| 39 | reservationStatus | 반복예약 (설정 직후 1, 수십 초 뒤 0 원복) |
| 59–60 | heatTempSaveOndol | 절약 모드 온돌 온도 |
| 61–62 | heatTempSave | 절약 모드 실내 온도 |
| 63 | gasUsageUnit | 가스 사용량 단위 |

- `modeStatus` enum: 0 꺼짐 · 1 절약 · 2 자동 · 3 정음 · 4 정음+절약 · 5 정음+자동 · 8 살균.
  운전/정음/살균이 **한 필드**다(독립 토글 아님).
- 개별 EPC 읽기는 미지원 — 어떤 EPC 로 `/get` 해도 `fa`→`70` 전체 블롭으로만 답한다.
- 위 표에 없는 니블(시운전·에러 상세·예약 종류·24시간/패턴 예약 등)은 현재 전부 0 또는 `fff` 라 미해독이다.

## 6. 각방 상태 블롭 (f09, 바이트·슬롯)

`fa` 응답 `70` = **55바이트**, 0부터. 7바이트 슬롯 7개(구역) + 공통값 6바이트.
슬롯 `s` = `byte[7s]`, 명령 선택자 `a0 = s+1`.

```
방1   방2   방3   방4   방5   방6   거실   공통
0–6   7–13  14–20 21–27 28–34 35–41 42–48  49–54
```

슬롯(7바이트): `[stat][예약h][00][현재°][설정°][시간분][00]`

| +byte | 필드 | 값 |
|---|---|---|
| +0 | stat (비트, 아래) | 비트맵 |
| +1 | 예약 시간 (`97`, 예약 꺼도 남음) | 1~24 16진 |
| +3 | 현재 온도 | °C 16진 |
| +4 | 설정 온도 (`d4`, 5~40°C) | °C 16진 |
| +5 | 시간모드 "1시간에 N분" (`da`, 기본 `0a`) | 분 16진 (`05`~`3c`) |

stat 비트:

| 비트 | 뜻 |
|---|---|
| `0x01` | 응답함 — 이 자리에 조절기가 지금 답함 (빈 슬롯 = `00`). 방 번호를 바꾸면 뺀 자리에 찌꺼기(켜짐·난방 비트나 마지막 온도)가 남을 수 있는데 이 비트가 꺼지므로, **방 존재는 이 비트로 판정**한다(린나이 서버/앱도 같다) |
| `0x02` | 켜짐 (난방 요청) |
| `0x04` | 시간 모드 (`b4=1`) |
| `0x08` | 예약 켜짐 (`96=1`) |
| `0x10` | 외출 (`b3=1`) |
| `0x40` | 난방 중 (밸브 열림) |
| `0x80` | 주 조절기 표식 (Wi-Fi 기기 슬롯, 예약은 이 방에서만 유지) |

공통값(byte 49–54): `49` = 온수 설정(`d1`), 나머지는 미해독.
각방은 온수 설정 등 **보일러 레벨 값도 제어**한다.

## 7. 사용량 통계 REST API

앱 "에너지 사용 정보"의 원자료. 보일러(f06)에만 있고, 각방(f09)으로 물으면 `E000005`.

```
GET https://www.rkiot.net/history/boiler/maintenance?group=hour|day|month
H-Filter: {"deviceId":…, "sCreate":<epoch>, "eCreate":<epoch>}   (HMAC 서명 + 로그인 토큰)
```

| group | 내용 |
|---|---|
| `hour` | 누계 스냅숏 한 시간에 한 줄 (빠진 시간·중복 있음) |
| `day` | 같은 누계의 하루 차이 (`create` = 그날 12:00 KST) |
| `month` | 달 합계 (`create` = 그 달 16일) |

### 원천 = 기기의 `stg` 메시지

보일러 Wi-Fi 모듈이 한 시간마다 `…/f06/<code>/{MAC}/stg` 로
`{"mnt":{"sum":6,"data":[{label,value}…]}}` 를 올린다.

| label | 뜻 |
|---|---|
| `d20` | 난방 버너 누계 시간 |
| `d21` | 온수 버너 누계 시간 |
| `d26` | 난방 가스 누계 ㎥ |
| `d27` | 온수 가스 누계 ㎥ |
| `d24`·`d25` | 펌웨어 버전 (rc·wifi) |

- 각방(f09)의 `stg` 는 자기 버전(`d24`·`d25`)만 싣는다.
- LYNNAI 허브는 프록시·단독 모드 모두에서 이 `stg` 를 받아 풀어 둔다(`/api/v1/state` 의 `boiler.usage`, 이벤트 `boil_stg`).
  단독 모드엔 클라우드가 없으므로 이게 유일한 원천이다.
- 앱 사용량은 보일러가 스스로 세는 가스 누계(0.1㎥ 단위)를 정수 ㎥ 로 **내림**한 값이다
  — 연소 시간에 정비례하지 않는다.
- 외부 펄스 계량기(1펄스 = 10 L)와 연소 니블(8·9)을 ms 로 맞춰 실측 연소율을 역산한다
  (안정 연소 ≈ 10 L / 68초). 허브의 "펄스 없음" 경고가 이 관계를 쓴다.

## 8. 모델코드별 온도 표

토픽 `…/f06/23/{MAC}` 의 두 자리 `23` 이 모델코드다. 앱은 이 값으로 온수·난방수(온돌) 설정에서
**고를 수 있는 값의 표**를 고른다(기기 이미지는 모델코드로 바뀌지 않는다). 보일러(f06)와 각방(f09)이 규칙이 다르다.

표의 값(°C):

| 표 | 값 |
|---|---|
| 난방수 22 | 40, 45~60, 65, 70, 75, 80, 85 |
| 난방수 23 | 35 + 위 |
| 난방수 13 | 40, 45, 47, 50, 52, 55, 57, 60, 65~85(5단위) |
| 온수 16 | 35~47, 50, 55, 60 |
| 온수 21 | 30~47, 50, 55, 60 |
| 온수 22 | 35, 36, 37~42.5(0.5단위), 43~47, 50, 55, 60 |
| 온수 27 | 30~36, 37~42.5(0.5단위), 43~47, 50, 55, 60 |
| 온수 3 · 7 | 온도가 아니라 1~3단 · 1~7단 (단 번호를 그대로 보냄) |

규칙:

- **보일러 f06**
  - 난방수 23: `04 05 06 0b 0c 21 24 25 28 29 2b 31 33 35 37 39 40 41 42`, 그 밖 22.
  - 온수 16: `00 01 02 0a 0d 0f 20 23 26 2a 30 32 34 36`.
  - 온수 22: `03 27 38` · 온수 27: `06 29 39` · 온수 21: `04 05 0c 21 25 28 2b 31 33 35 37`.
  - 그 밖 3단.
- **각방 f09**
  - 십의 자리 `2`→난방수 23, `4`→13, 그 밖 22. `ff` = 온수 전용(난방수 조절 없음).
  - 십의 자리가 `0`·`2`·`4` 일 때 일의 자리 `1`→7단, `2`→22, `3`→16, `4`→21, `5`→27. 그 밖 3단.

허브는 토픽의 모델코드를 기억해 드라이버·HA 에 알리고(업링크 메시지 `0x0d`, 상태 API `model`),
둘이 이 규칙으로 설정 범위·0.5 단위·단 번호를 고른다. 모델코드를 모르는 옛 펌웨어에서는 실측 기본표를 쓴다.
구현은 `firmware/esp32/main/hub_rinnai.c`·`edge-driver/src/core.lua`·`custom_components/lynnai_hub/protocol.py`.

## 9. 구형 플랫폼 (참고, 우리와 다름)

공개 프로젝트(mog422/open-rinnai-server, zobithecat·sasamix 등)의 대상은 구형 "스마트 Wi-Fi 실내온도조절기"
(WF-S100 / WF-100W 계열)다. 서버 `wifiboilers1.rinnai.co.kr`, TCP 9105 평문 폴링 계열이다.
신형 `rkiot`(이 문서) 플랫폼을 다룬 공개 프로젝트는 찾지 못했다 — 기능 이름은 겹치지만 프로토콜은 다르다.
